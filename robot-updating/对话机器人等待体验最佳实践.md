# 语音对话机器人:缓解「STT → Agent 查数 → TTS」等待的最佳实践

> 适用场景:用户说完话 → ASR → 大模型判断意图 → 调用后台 agent/工具(查数、检索、多步操作)
> → 生成答案 → TTS 播报。**等待窗口 = 工具耗时**,常见 10 秒到数分钟,且**方差极大**。
>
> 本文是设计参考,针对米宝一号(StackChan + xiaozhi-server + 广西植保 S2S)的落地对照见第 8 节。

---

## 1. 先定延迟预算(有据可依)

| 阈值 | 含义 | 该做什么 |
|---|---|---|
| **0.1 s** | 用户感觉"系统在直接响应"的上限 | 确认收到:earcon 提示音 / LED / 表情,不等 ASR 完成 |
| **1 s** | 用户思绪流不被打断的上限 | 超过 1 s 必须给"正在处理"信号 |
| **2 s** | 业界语音 Agent 框架的默认"开始垫话"阈值 | 播 interim(先应答) |
| **10 s** | 用户注意力上限 | 需要**真实进度指示 + 明确的打断入口**;超过即转异步 |

**最重要的一条**:响应时间**波动越大,反馈越重要**——因为用户完全不知道要等多久。
参考:[NN/g《Response Times: The 3 Important Limits》](https://www.nngroup.com/articles/response-times-3-important-limits/),
[Microsoft Voice Live `interim_response`](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-voice-live-interim-response)。

> 实用推论:**别按"毫秒级延迟"设计,按"分钟级后台任务"设计。**

---

## 2. 五层实践(按时间轴)

### L0. 0–0.3 s:确认收到(不等 ASR)
- 声学 earcon(短提示音)、LED 呼吸/变色、面部表情、点头动作。
- 语音场景**不能只靠"看"**,earcon 是唯一普适的即时反馈手段。
- 参考:[Alexa Natural Speech](https://developer.amazon.com/ja-JP/alexa/alexa-haus/natural-speech#ask-questions)。

### L1. 0.3–2 s:先应答(interim response)
- 两种实现:

  | 方式 | 优点 | 代价 |
  |---|---|---|
  | 静态文案列表(随机选一句) | 可控、零推理成本、品牌语气统一 | 变化少,可能重复 |
  | 轻量 LLM 生成 | 上下文相关、自然 | 多一次推理成本与延迟 |

- **双触发**优于单触发:`tool`(一调用工具就说)+ `latency`(超过阈值也说),两者 OR。
- 三条硬约束:
  1. **不进入对话历史**(否则污染上下文,还可能破坏 `tool_calls → tool(result)` 配对);
  2. **不遮挡真正的答案**(答案出来时 filler 必须已结束);
  3. **必须可被 barge-in 打断**。
- 建议文案(中文,降调略慢):
  「正在为您查询,请稍等一下。」/「这个要查一下后台数据,稍等。」
  **避免**:"嗯…"、"让我想想"这类无信息填充。

### L2. 2–10 s:让进度可见
四种手段,按性价比排序:

1. **流式输出**:能多早出第一个 token 就多早(受后端限制时此路不通)。
2. **阶段化真实进度**(收益最大):把 agent 的真实阶段翻译成人话播出来。
   - agent 框架通常已经在推 `thinking` / `tool_call` / `step` 事件,把它们映射成 3–5 个里程碑;
   - **节流**:每 20–30 秒最多播一次,只播里程碑,不播细节;
   - 例:「正在查广西的监测数据」→「查到了,正在整理」。
3. **结果上屏**:设备有屏幕时,把表格/明细放屏幕,**语音只播 1–2 个关键数字**。
4. **内容占位**:先播已知的常识/背景部分,数据回来再补。

### L3. >10 s:异步任务化 + 主动播报
- 工具**立即返回**一句应答 → 后台继续跑 → 数据回来**主动播报**(task-completion pattern)。
- **保活**:长任务期间持续刷新会话活动时间,避免被"无语音超时"掐断。
- **播报时机**:等用户当前一轮说完、环境安静再播,避免打断。
- **取消语义**:用户说"算了/不用了"要能真正取消后台任务并停止后续播报。
- **过期处理**:结果回来时用户已换话题 → 改为屏幕提示或一句带过,不要硬打断。
- 参考:[Alexa Progressive Response API 实践](https://developer.amazon.com/en-US/blogs/alexa/post/f952eca8-7f6f-4490-85d8-a805b50f6d25/alexa-skill-recipe-improving-the-perceived-latency-of-api-calls-using-the-progressive-response-ap)。

### L4. 压缩真实耗时(最根本)
1. **收窄查询**:在工具描述里约束字段数/时段/粒度。字段越多、时段越长,后端 agent 轮数越多。
2. **预热/预取**:高频问题定时预查并缓存。
3. **复用**:同一会话内相同问题复用结果(注意额度成本)。
4. **幂等 + 去重**:防止一次提问触发 2–3 次真实调用。
5. **有界等待 + 降级**:见第 4 节。

## 3. 有界等待与降级矩阵(建议值)

| 已等待 | 动作 |
|---|---|
| 0–0.3 s | 即时反馈(earcon/LED) |
| 2 s | interim:「正在查询,请稍等」 |
| 20–30 s | 第二句:真实阶段进度(换一句,不重复) |
| 60 s | 「还在查,这类数据一般要一分钟左右」——**给预期** |
| 120 s | 转「稍后告诉你」+ 屏幕提示,释放对话让用户问别的 |
| 超时/失败 | 明确说出真实原因 + 替代问法(不要笼统说"没查到") |

⚠️ **坑**:很多框架配的 `timeout` 是**单次读超时**,不是总时长。如果后端一直有流式心跳/思考文本,接口可以跑几分钟而不触发超时(米宝实测跑到 308 秒)。要限制等待必须**自己做总时长看门狗**。

---

## 4. 反模式(别这么干)

- ❌ 让用户干等到答案出来,全程无任何声音/视觉反馈。
- ❌ filler 写进对话历史(污染上下文,破坏 tool_call/tool result 配对)。
- ❌ 结果播报直接打断用户正在说的话。
- ❌ 无上限等待,或依赖"单次读超时"当总超时。
- ❌ 每次都说同一句 filler。
- ❌ 结果已过期(用户换了话题)还硬播。
- ❌ 把 agent 的技术细节/思考原文念给用户听。
- ❌ 超时后只回"抱歉我没查到",不说真实原因,让用户误以为是自己的问法问题。

## 5. 可观测性(否则无法优化)

分阶段埋点,按问题类型分组:

| 指标 | 说明 |
|---|---|
| ASR 耗时 | 说完 → 出文本 |
| LLM 决策耗时 | 文本 → 决定调工具 |
| 工具/接口耗时 | 发出请求 → 数据返回(**p50/p95/p99**) |
| 内部阶段耗时 | 若后端发进度事件,拆出"查库/生成" |
| TTS 首音耗时 | 文本入队 → 实际出声 |
| 用户感知总时长 | 说完 → 听到数据 |
| interim 命中率 / 超时率 / 取消率 / 过期播报率 | 体验质量 |

**按维度下钻**:字段数、时段长度、单点 vs 全域、是否同会话复问——通常能立刻找到"哪种问法慢"。

## 6. 实施检查清单

- [ ] 0.3 s 内有即时反馈(earcon/LED/表情)
- [ ] 工具一调用就有 interim(不入历史、可打断)
- [ ] 同时有 `latency` 触发(大模型慢时也说一句)
- [ ] agent 的阶段事件已映射为 3–5 个人话里程碑,并节流
- [ ] >20 s 有第二句不同文案
- [ ] >60 s 给出预期时长
- [ ] >120 s 转异步/屏幕提示,释放对话
- [ ] 有总时长看门狗(不依赖单次读超时)
- [ ] "算了"能真正取消后台任务
- [ ] 结果回来时判断是否已过期/换话题
- [ ] 表格类结果上屏,语音只播关键数字
- [ ] 查询字段数有约束,避免大模型自作主张加字段
- [ ] 高频问题有预热/缓存
- [ ] p50/p95 分阶段埋点 + 按问题类型下钻

## 7. 米宝一号的落地对照

> 2026-10-08 已完成第一轮"用户体贴优化"(服务端,配置可开关):
> 分级进度播报 + 有界等待 + 迟到开场白 + 收窄查询 + 分阶段埋点。

| 实践 | 现状 | 建议 | 收益 |
|---|---|---|---|
| tool 触发 interim | ✅ 框架 ack(静态文案) | 保持 | — |
| 真实进度播报 | ✅ **本轮新增**:25/60/110 s 分级播报,正文一开始流式返回即停止 | 下一步:把平台 `stepTitle` 映射成具体阶段话术(埋点已采集) | **高** |
| 有界等待/降级 | ✅ **本轮新增**:`query_deadline_seconds: 360` + 可操作超时话术 | 可按业务调小 | 中高 |
| 迟到开场白 | ✅ **本轮新增**:超 90 s 改口"不好意思让您久等了" | — | 低 |
| 收窄查询 | ✅ **本轮新增**:工具描述限定"只查用户问到的字段,默认最近一周" | 看 `[PHYTO-TIMING]` 里字段是否变少 | **高** |
| 可观测性 | ✅ **本轮新增**:每次查询一行 `[PHYTO-TIMING]` | 下一步:脚本统计 p50/p95 | 中 |
| 结果上屏 | ⚠️ 气泡只显示文字 | 表格/明细上屏,语音只播关键数字 | 中 |
| 取消语义 | ⚠️ `client_abort` 部分处理 | "算了"→ 取消后台任务 | 中 |
| 结果过期处理 | ❌ 无 | 判断是否已换话题 | 低 |
| 即时反馈(earcon) | ⚠️ 唤醒后有,等待期无 | 加"收到"提示音(需固件) | 低 |
| 去重 / 保活 / 等安静再播 | ✅ 已实现 | 保持 | — |

**可调开关**(`data/.config.yaml` → `plugins.ask_guangxi_phyto`):

```yaml
progress_enabled: true
progress_messages:
  - { at: 25,  text: "后台正在查省级植保数据，请稍等一下。" }
  - { at: 60,  text: "还在查，这类数据一般要一分钟左右，您稍等。" }
  - { at: 110, text: "数据量有点大，还在处理，查到我马上告诉您。" }
progress_min_gap_seconds: 15
progress_quiet_wait_seconds: 6
query_deadline_seconds: 360
late_announce_seconds: 90
async_late_prefix: "不好意思让您久等了，"
```

**一句话**:0.1 s 确认收到 → 2 s 内先应答 → 10 s 内给真实进度(用 agent 已有的阶段事件)→
超 10 s 异步化 + 主动播报 + 可打断;同时用"收窄查询 + 预热缓存"把 p50 压到 10 秒量级。
