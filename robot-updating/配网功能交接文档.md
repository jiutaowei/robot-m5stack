# 米宝一号（StackChan）— 配网功能交接文档

> 本文档记录配网功能的**总体目标、当前进展、堵塞点、资料与源码索引**，供后续接手者快速恢复上下文。
> 最后更新：2026-08-08

---

## 一、总体目标

让 **米宝一号（Mibao One）**（基于 M5Stack StackChan / ESP32-S3 硬件）具备**可靠、可上手的 WiFi 配网能力**：

1. **首次开机（无已保存 SSID）**：自动进入配网模式，用户手机连热点 → 浏览器配网 → 自动连上 WiFi。
2. **配网成功后**：进入米宝 launcher（正常产品界面），可正常使用对话、会议录音、文件管理等功能。
3. **二次开机（有 SSID）**：跳过配网，直接进入 launcher，联网功能正常。

**目标体验对标**：M5Burner 官方 `StackChan-MCP 4 Any LLM` / `xiaozhi v2.6.6` 固件——开机即配网、配网一次成功、不崩溃、不闪退。

## 二、硬件与软件架构

| 项 | 说明 |
|----|------|
| 硬件 | M5Stack StackChan（ESP32-S3，CO5300/ILI9342 屏幕，AXP2101 PMU，SD 卡） |
| 主框架 1 | **mooncake**（`main/apps/*`）：launcher + 米宝各功能 app |
| 主框架 2 | **xiaozhi-esp32**（vendored 于 `fw/xiaozhi-esp32/`）：AI 对话 + 原生 WiFi 配网 |
| 启动流程 | `app_main` → `GetHAL().init()` → mooncake 循环 → `startXiaozhi()` |
| 板级 | `M5StackCoreS3Board`（继承 xiaozhi 的 `WifiBoard`）→ 具备 xiaozhi 原生配网能力 |

**关键架构结论**：xiaozhi 原生配网（`WifiBoard::StartNetwork`）**已经内置在本项目**，与 M5Burner 官方固件同源。问题在于本项目用 mooncake launcher 层时，配网曾由自定义 worker 接管导致闪退。

## 三、目前进展（配网方案演变历程）

### 3.1 已稳定完成（非配网部分）
- 编译流程固化：`scripts/build.sh`（增量 / `full` 全量 / `menuconfig`），解决 ESP-IDF venv、日志目录、ninja 锁等踩坑。
- 烧录脚本：`scripts/flash.sh [串口] [erase]`。
- 文件管理、录音、会议录音、IoT、个人灵感等米宝 app 已可编译并在 launcher 显示。

### 3.2 配网方案反复尝试（按时间）
1. **原生引导（StartupWorker）**：无 SSID 时显示 M5 二维码引导页 → 需手机 App，不符合"浏览器配网"需求 → 弃用。
2. **自定义 HotspotSetupWorker**（mooncake 阶段，`app_setup/workers/connectivity.cpp`）：手机连热点 → 192.168.4.1 配网。**配网提交后设备闪退**。
3. **修复：StartStation 移出 LVGL 线程**（独立高栈任务）→ 仍闪退。
4. **修复：StartConfigAp / StopConfigAp 均移独立任务** → 仍闪退。
5. **方案：submit 保存后主动 `esp_restart()`**（绕开 AP→STA 切换）→ 用户反馈仍"闪退"。
6. **（当前）xiaozhi 原生配网移植**：无 SSID 时 `skip_mooncake` 直接进 xiaozhi 配网，配网成功 `WifiBoard` 检测到"本轮配过网"后主动重启回 launcher → **用户最新反馈"还是不行"**。

### 3.3 关键结论
- xiaozhi 原生配网（`WifiBoard` 事件驱动重连）与官方固件同源，**理论上最可靠**。
- 但**至今未拿到串口日志**，无法确认"闪退"到底是 **panic 崩溃** 还是 **主动/意外重启**，也无法定位崩溃行。这是当前最大障碍。

## 四、当前堵塞点（最重要）

### 4.1 堵塞点 1：配网后设备闪退/重启，根因未定位（★最优先）
- **现象**：手机配网页显示"配置成功"，随后设备立即重启/闪退。
- **疑点**：未确认是 panic（`Guru Meditation Error` / `aborted`）还是主动 `esp_restart()`。
- **阻塞原因**：串口日志工具打开异常，未获得崩溃栈。
- **必须动作**：抓取串口日志（见第六节），拿到 panic 地址后，用 `addr2line` / `idf.py` 定位崩溃函数。

### 4.2 堵塞点 2：mooncake 与 xiaozhi 双框架配网节奏冲突
- 配网在 mooncake 阶段（自定义 worker）和 xiaozhi 阶段（原生）用了两套逻辑，容易互相干扰（如 ESP-NOW 的 `hal_espnow.cpp` 可能重复初始化 esp_wifi）。
- 当前方案 `skip_mooncake` 已让无 SSID 时走 xiaozhi 原生，但仍需验证是否真正生效。

### 4.3 堵塞点 3：M5Burner 官方固件可配网，但无法反编译利用
- 官方 `StackChan-MCP` / `xiaozhi v2.6.6` 配网正常（用户实测），但编译产物是 `.bin`，无法直接改成我们的 launcher 形态。
- 已有参考价值的是**官方源码**：`/Users/cobain/Documents/stackchan-mcp-analysis/`（StackChan-MCP 完整源码，含 `78__esp-wifi-connect` 配网组件）。

## 六、下一步建议（按优先级）

1. **【最高优先】抓串口日志，定位闪退根因**
   烧录后运行（或用 Arduino IDE 串口监视器，波特率 115200）：
   ```bash
   /Users/cobain/.espressif/python_env/idf5.5_py3.14_env/bin/esptool.py \
     --chip esp32s3 -p /dev/tty.usbmodem1301 monitor
   ```
   - 若看到 `Guru Meditation Error` / `aborted` / `Backtrace` → **panic 崩溃**，把 backtrace 发接手者，用 `xtensa-esp32s3-elf-addr2line` 定位。
   - 若看到 `Provisioning success, rebooting to launcher` → 是**主动重启**，问题在重启之后。

2. **确认当前 xiaozhi 原生配网方案是否真实生效**
   烧录后开机应**直接进配网**（屏幕显示热点提示），而非进 launcher。若仍进 launcher，说明 `skip_mooncake` 的 SSID 判断 / NVS 未按预期。

3. **对比验证**：用 M5Burner 烧官方 `StackChan-MCP`，确认它在本硬件上配网正常（用户已确认），再对照 `stackchan-mcp-analysis` 源码逐行核对差异。

4. **排查 ESP-NOW 冲突**：检查 `hal_espnow.cpp` 是否在启动时重复初始化 esp_wifi，与配网冲突。

## 七、通用注意事项

- 配网问题多次迭代仍未根治，**务必基于日志修复，勿再盲改**。
- 修改 `managed_components/` 或 `xiaozhi-esp32/` 会同时影响 xiaozhi 正常逻辑，改动前先确认影响面。
- 本硬件 GPIO35/36/37 为 LCD/SD 共享引脚，SD 相关操作会与配网无关，但排查闪退时留意。
- 主分支代码以 `robot-updating/fw` 为准；`build.sh` 会 rsync 到 `/Users/cobain/robot-build/fw` 再编译。
