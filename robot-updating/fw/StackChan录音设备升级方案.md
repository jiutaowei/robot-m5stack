# StackChan 录音设备升级方案

## 1. 文档目的

本文基于当前 StackChan 固件中的录音、音频驱动、SD 卡存储、上传协议和会议界面代码，整理后续升级内容。

当前固件已经具备以下基础能力：

- StackChan 麦克风采集；
- 单声道 PCM16 WAV 文件保存；
- SD 卡挂载和共享 SPI/LCD 处理；
- 录音开始、暂停、结束界面；
- WAV 文件头回写；
- 上传协议、Manifest、分段存储等基础类；
- 部分主机侧单元测试。

当前整体定位仍然是“录音功能验证版”，距离稳定、可恢复、可长期运行的录音设备还需要完成以下升级。

## 2. 总体目标

升级后的设备应满足：

1. 采样率、时间戳、WAV 文件头和上传协议完全一致；
2. 录音过程不依赖 UI 主循环，不因 SD 卡或网络阻塞而丢音频；
3. 支持长时间录音、自动分段和断电恢复；
4. SD 卡异常、麦克风异常、低电量等情况可以被检测和提示；
5. 本地录音、网络上传、实时转写的状态真实可靠；
6. 录音具有明确的状态、隐私提示和文件管理能力；
7. 通过真实 StackChan 硬件上的长时间和异常场景测试。

## 3. 升级优先级

| 优先级 | 含义 | 内容 |
|---|---|---|
| P0 | 必须优先完成 | 影响录音正确性、稳定性或数据完整性 |
| P1 | 核心功能完善 | 影响长期使用和设备可维护性 |
| P2 | 产品化增强 | 提升体验、效率和安全性 |

## 4. 具体升级内容

### P0-1：统一音频采样率和时间基准

#### 当前问题

硬件配置使用 24 kHz 输入，而 WAV 文件和录音协议按照 16 kHz 处理。`AudioBlock` 每次包含 320 个采样，并被标记为 20 ms，但 320 个采样在 24 kHz 下只有约 13.3 ms。

这会导致：

- WAV 播放速度和录音时长不准确；
- 上传时间戳错误；
- 转写结果与音频位置不一致；
- 分段边界和 ACK 序号无法准确对应真实音频时间。

#### 升级方案

推荐以 16 kHz、单声道、16 bit 作为录音和上传的统一格式：

1. 确认麦克风输入实际采样率；
2. 如果硬件必须使用 24 kHz，则增加 24 kHz 到 16 kHz 的重采样；
3. 将音频块固定为 320 个 16 kHz 采样，即 20 ms；
4. WAV 头、Manifest、SCMT 协议和时间戳全部使用同一采样率；
5. 输入设备使用 `input_sample_rate_`，不要使用输出采样率代替输入采样率；
6. 增加采样率和时间戳的自动化测试。

#### 验收标准

- 使用音频分析工具检查 WAV 文件采样率为 16 kHz；
- 录制 60 秒，文件播放时长误差小于 1%；
- 每个音频块的时间戳间隔稳定为 20 ms；
- 上传协议中的音频时间轴与本地 WAV 一致。

### P0-2：将录音流程从 UI 主循环中拆出

#### 当前问题

当前 `AppMeeting::onRunning()` 中同步完成音频读取和 SD 写入。SD 卡写入、共享 SPI 切换或文件系统操作可能阻塞 UI，也可能导致音频采集不及时。

#### 升级方案

改为三层任务结构：

```text
I2S/DMA 采集任务
        ↓
音频 RingBuffer
        ↓
SD 写入任务
        ↓
网络上传任务
```

具体实现：

1. 采集任务只负责从音频驱动读取数据；
2. 使用 FreeRTOS RingBuffer 或队列传递固定大小音频块；
3. SD 写入任务批量写入多个音频块；
4. 网络上传任务独立运行，不能阻塞本地录音；
5. UI 只读取状态和统计信息；
6. 记录队列深度、丢帧数和写入延迟；
7. 为采集任务和 SD 写入任务设置合理的任务优先级。

#### 验收标准

- 录音过程中界面无明显卡顿；
- Wi-Fi 断开时本地录音继续；
- SD 写入速度变慢时采集任务不立即丢帧；
- 连续录音 2 小时无看门狗复位。

---

### P0-3：修复音频读取错误处理

#### 当前问题

底层 `CoreS3AudioCodec::Read()` 当前即使 `esp_codec_dev_read()` 失败，也可能返回请求的采样数，上层因此无法区分读取成功和读取失败。

应用层遇到读取失败时也只是直接返回，没有显示错误或记录丢帧。

#### 升级方案

1. 让底层读取函数返回真实读取结果；
2. 定义明确的读取状态，例如：成功、暂时无数据、设备错误、DMA 错误；
3. 记录总采样块数、失败块数、连续错误数和丢帧数；
4. 短暂错误时插入静音块并记录缺口；
5. 连续错误超过阈值后停止录音并提示用户；
6. 在日志中输出错误码，但避免高频刷屏。

#### 验收标准

- 模拟 I2S 读取失败时，应用能够进入明确错误状态；
- 音频文件不会把错误数据误认为有效音频；
- UI 能显示麦克风错误或音频丢帧提示。

---

### P0-4：接入安全的分段录音机制

#### 当前问题

代码中已经定义了 5 分钟分段和 `SegmentStore`，但实际 `AppMeeting` 仍然只打开一个 WAV 文件，分段逻辑没有接入主录音流程。

长时间录音可能遇到：

- WAV 32 位大小字段限制；
- 单文件损坏导致整场会议不可用；
- SD 卡写入失败后无法定位具体损坏区间；
- 上传和恢复粒度过大。

#### 升级方案

每 5 分钟生成一个音频分段：

```text
000000.part  → 000000.wav
000001.part  → 000001.wav
000002.part  → 000002.wav
```

具体步骤：

1. 当前分段先写入 `.part` 文件；
2. 写入过程中周期性刷新文件；
3. 分段结束时回写 WAV 头；
4. 完成校验后将 `.part` 原子改名为 `.wav`；
5. 生成对应的采样起始位置、采样数量和 SHA-256；
6. 更新 Manifest；
7. 下一段从准确的起始采样序号继续。

#### 验收标准

- 10 分钟录音生成两个有效 WAV 文件；
- 两个分段之间没有重复或丢失采样；
- 每个分段可以独立播放；
- 分段边界时间和采样序号连续。

---

### P0-5：实现断电、重启和异常恢复

#### 当前问题

当前文件只有在正常结束录音时才回写最终 WAV 头。设备在录音中断电或重启时，当前文件可能无法播放，已有的恢复类也没有接入启动流程。

#### 升级方案

1. 启动时扫描所有 `.part` 文件；
2. 检查文件长度是否为合法 WAV 数据长度；
3. 根据实际 PCM 数据重新生成 WAV 头；
4. 校验 SHA-256 或文件长度；
5. 恢复成功后原子改名为 `.wav`；
6. 更新 Manifest 中的分段状态；
7. 恢复失败时保留原文件，并在 UI 中显示可处理错误；
8. Manifest 使用临时文件写入后再原子替换；
9. 适当保留一个 `.bak` Manifest，防止 Manifest 自身损坏。

#### 验收标准

- 录音过程中重启可以恢复最后一个分段；
- 恢复后的 WAV 能正常播放；
- 恢复不会重复或跳过音频块；
- Manifest 损坏时可以通过分段文件重新构建。

---

### P0-6：明确并接通实际上传流程

#### 当前问题

当前代码中虽然存在 `MeetingUploader`、WebSocket 传输接口、ACK、重连和 Manifest，但 `AppMeeting` 没有实际创建和调用上传器。录音结束后会直接显示“Waiting for server API”，随后进入完成状态。

因此当前的上传和转写属于接口及测试代码，并不是真实设备功能。

#### 升级方案

明确支持以下两种模式：

#### 本地录音模式

- 只采集并保存到 SD 卡；
- 录音结束后显示文件路径和文件大小；
- 提供之后上传或导出的入口。

#### 实时会议模式

- 建立 WSS 连接；
- 发送设备身份、会议 ID、采样率和编码格式；
- 实时发送音频块；
- 接收并持久化 ACK；
- 网络断开时继续本地录音；
- 网络恢复后补传未确认分段；
- 接收实时转写事件并更新界面；
- 只有服务器确认完成后才显示“上传完成”。

#### 验收标准

- Wi-Fi 断开 3 分钟期间录音不中断；
- Wi-Fi 恢复后缺失分段能够补传；
- ACK 重启后仍能恢复；
- 服务器返回的转写内容能正确显示在 UI；
- 上传失败时不能错误显示“Completed”。

---

### P0-7：完成真实 StackChan 硬件测试

#### 当前问题

当前测试主要覆盖纯逻辑代码，真实 StackChan 上的录音、SD 卡、LCD 共享总线、网络恢复和断电恢复尚未完成验证。

#### 升级方案

建立硬件回归测试流程：

1. 启动和 SD 卡挂载测试；
2. 1 分钟录音和 WAV 可播放测试；
3. 10 分钟分段录音测试；
4. 2 小时连续录音测试；
5. 录音中断电重启测试；
6. Wi-Fi 断开和恢复测试；
7. SD 卡拔出和重新插入测试；
8. 低电量自动停止测试；
9. UI、舵机、AI Agent、Avatar 等原有功能回归测试；
10. 检查内存、任务栈、队列深度和看门狗状态。

所有测试应记录：固件版本、硬件版本、SD 卡型号、录音时长、文件大小、错误日志和测试结论。

### P1-1：提升 SD 卡写入效率和可靠性

#### 升级方案

1. 使用固定大小的 DMA/RingBuffer 缓冲区；
2. 一次写入多个音频块；
3. 避免每个采样调用一次 `fwrite`；
4. 录音期间定期 `fflush`；
5. 分段结束时执行同步操作；
6. 监控实际写入耗时；
7. 检查剩余空间，提前预估可录音时长；
8. 处理 SD 卡拔出、写满和文件系统错误；
9. 尽量减少每个音频块都停止和恢复 LCD 总线的次数。

### P1-2：优化内存和实时性

#### 升级方案

1. 复用音频输入缓冲区；
2. 避免在每次采集时创建 `std::vector`；
3. 对 RingBuffer、网络缓冲和文件缓冲设置固定上限；
4. 使用 PSRAM 保存较大的非实时缓存；
5. 统计堆内存、最小剩余内存和任务栈余量；
6. 避免使用 `erase(begin())` 这种 O(n) 队列操作，改用环形队列或 FreeRTOS 队列。

### P1-3：完善暂停、结束和异常状态机

#### 升级方案

1. 明确暂停是否计入录音时长；
2. 暂停时刷新当前文件状态；
3. 结束时进入真实的 Finalizing 状态；
4. 文件保存成功后才能进入 Completed；
5. 上传完成和本地保存完成分开表示；
6. 错误状态中保存错误类型和错误码；
7. 允许用户重试上传，而不是重新录音；
8. 应用退出时弹出“正在录音”的确认提示。

### P1-4：增加音频质量处理

#### 升级方案

根据使用场景选择处理链路：

- 高通滤波：去除低频震动和桌面噪声；
- NS：降低环境噪声；
- AGC：保持语音音量稳定；
- Limiter：防止削波；
- VAD：识别有效语音区间；
- AEC：有扬声器播放时抑制回声；
- 削波检测：提示麦克风增益过高；
- 音量校准：使不同设备录音电平一致。

建议保留原始录音和在线处理链路的区分：本地文件优先保存稳定的原始或轻处理数据，实时转写可以使用 AEC、NS 和 AGC 后的数据。

### P1-5：完善存储和文件管理

#### 升级方案

增加：

- 录音列表；
- 录音日期和时长显示；
- 文件大小显示；
- 播放或试听；
- 删除录音；
- 上传状态；
- 失败重试；
- 剩余空间显示；
- 自动清理策略；
- 录音文件唯一命名。

文件名不要只依赖启动后的 `millis()`，建议使用 RTC 时间、设备 ID、随机 UUID 和序号组合，避免设备重启后发生重名。

### P1-6：处理电量、功耗和热管理

#### 升级方案

1. 录音时关闭不必要的舵机和扬声器；
2. 低电量时禁止开始长时间录音；
3. 录音中低电量时先安全结束当前分段；
4. 监控 PMIC、电池电压和设备温度；
5. 显示预计剩余录音时间；
6. 防止系统自动休眠或关机破坏录音文件。

## 5. 音频、存储和网络数据模型建议

建议每场录音对应一个目录：

```text
/sdcard/meetings/20260714_153012_a83f/
├── manifest.json
├── 000000.wav
├── 000001.wav
├── 000002.part
└── events.log
```

Manifest 至少包含：

```json
{
  "meetingId": "20260714_153012_a83f",
  "deviceId": "stackchan-001",
  "sampleRate": 16000,
  "channels": 1,
  "bitsPerSample": 16,
  "createdAt": 0,
  "durationMs": 0,
  "lastAckSequence": 0,
  "segments": []
}
```

每个分段建议包含：

- 分段序号；
- 起始采样序号；
- 采样数量；
- 起始时间和结束时间；
- 文件路径；
- 文件大小；
- SHA-256；
- 是否已上传；
- 是否已确认；
- 错误和重试次数。

## 6. 网络和安全升级

### 升级方案

1. 使用 WSS，而不是明文 WebSocket；
2. 正确校验证书；
3. Token 不写入普通日志；
4. 支持 Token 过期和刷新；
5. 设备 ID 和会议 ID 分离；
6. 上传前确认服务器端协议版本；
7. 对音频帧增加最大长度检查；
8. 增加帧校验或完整性校验；
9. 防止重复上传和 ACK 回退；
10. 本地录音和上传权限分别控制。

## 7. 用户体验和隐私升级

### 升级方案

- 开始录音时播放提示音；
- 使用明确的红色录音指示灯或屏幕图标；
- 增加物理或触摸静音操作；
- 显示“本地保存”“上传中”“上传失败”等真实状态；
- 录音时禁止误触退出；
- 显示文件时长、大小和剩余空间；
- 增加录音删除确认；
- 增加隐私和会议录音提示；
- 将硬编码英文 UI 纳入多语言资源；
- 转写内容只显示服务器真实返回的数据，不使用演示文本冒充结果。

## 8. 推荐开发顺序

### 第一阶段：保证录音正确

1. 统一 16 kHz 音频链路；
2. 修复底层读取错误返回；
3. 建立 RingBuffer；
4. 将 SD 写入放入独立任务；
5. 完成 1 分钟和 10 分钟硬件测试。

### 第二阶段：保证数据安全

1. 接入 `.part` 分段写入；
2. 接入 Manifest；
3. 实现启动恢复；
4. 增加 SD 卡异常和剩余空间处理；
5. 完成断电、拔卡和 2 小时测试。

### 第三阶段：接通网络功能

1. 明确服务器协议；
2. 实现 WSS Transport；
3. 接入 ACK 和重连；
4. 接入分段补传；
5. 接入真实转写事件；
6. 完成离线、恢复和重复上传测试。

### 第四阶段：产品化

1. 文件列表和播放；
2. 录音权限和隐私提示；
3. 音频增强；
4. 电量和功耗优化；
5. 安全升级；
6. 多语言和完整 UI 优化。

## 9. 最终验收标准

只有满足以下条件，才建议将设备视为稳定录音设备：

- 采样率和时间戳经过验证；
- 连续录音 2 小时无丢帧和复位；
- 10 分钟以上录音可以正确分段；
- 录音中重启后能够恢复；
- SD 卡写满或拔出时不会破坏已有文件；
- Wi-Fi 断开时本地录音不受影响；
- Wi-Fi 恢复后能够补传；
- 上传失败不会错误显示完成；
- 真实转写内容可以正确显示；
- 录音过程中有明确的隐私和状态提示；
- 原有 StackChan 的 AI、Avatar、舵机、显示和 OTA 功能保持正常。
