## 一、配网问题解决说明

### 1. 问题现象
手机连接设备热点（xiaozhi_xxx 或 mibao_xxx）、在 192.168.4.1 页面提交 Wi-Fi 密码后，设备**必现 abort 重启**，陷入重启循环。原生 xiaozhi 配网与自建 Hotspot Setup 两条路径全部失败。

### 2. 排查历程（走过的弯路，供后续避坑）
| 轮次 | 假说 | 结果 |
|---|---|---|
| 1 | WifiManager 未初始化，AP 起不来（SSID 显示 "starting"） | 修好了 AP 启动，但提交后仍失败 |
| 2 | worker 轮询时序滞后、超时窗口过短（15s→45s + 事件回调接力） | 提交后变为重启循环 |
| 3 | 事件回调里同步 StartStation，驱动刚 stop（上层时序 bug） | 回调改原子标志+延迟 2s，仍重启 |
| 4 | **抓 USB 日志 + addr2line 解码 backtrace，锁定底层时序 bug** | ✅ 根治 |

关键转折：把日志控制台切到 USB-Serial-JTAG（`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`）后抓到了 panic backtrace，解码直指崩溃行——此前所有假说都是无日志盲猜。

### 3. 最终根因（两层）

**① 底层根因（决定性）**：`managed_components/78__esp-wifi-connect/wifi_station.cc::Start()` 在 `esp_wifi_start()` **之前**调用 `esp_wifi_set_band_mode()`。驱动处于停止态返回 `ESP_ERR_WIFI_NOT_STARTED(0x3002)`，被 `ESP_ERROR_CHECK` 放大为 abort。
- 佐证：同组件 `wifi_configuration_ap.cc` 里相同调用放在 start **之后**（正确写法），两处代码不一致，一处埋雷；IDF 文档要求此类 API 在 start 后调用。
- 两条配网路径共用 `WifiStation::Start()`，所以一处修复两路全通。

**② 上层叠加问题**：HotspotSetupWorker 曾在配网退出事件的**同步通知链**里立即调 StartStation，此时驱动刚被 `esp_wifi_stop`，即使没有①也是错误时序。

### 4. 修复内容
| 位置 | 改动 |
|---|---|
| `wifi_station.cc`（托管组件，已加 patch 注释） | `set_band_mode` 移到 `esp_wifi_start()` 之后；`ESP_ERROR_CHECK` 降级为警告日志（ESP32-S3 仅 2.4G，该调用非关键） |
| `app_setup/workers/connectivity.cpp` | 事件回调零捕获只置静态原子标志；StartStation 延迟 2s 由轮询侧在独立 16KB 高栈任务执行；先校验 SsidManager 有凭证；Finishing 超时 45s |
| `xiaozhi-esp32/main/boards/common/wifi_board.h/.cc` | 新增 `AllowAutoWifiConfigMode()` 虚钩子，门控"开机自动弹配网热点"（默认关，走 mibao NVS `auto_prov` 键） |
| `main/hal/board/stackchan.cc` | override 钩子返回 `mibao::isAutoProvisioningEnabled()` |

### 5. 验证结果（2026-08-08 用户真机确认）
- Hotspot Setup 提交 jinhetech 密码 → **不再重启，显示 Connected**
- 物联网控制按钮点击成功（同链路修复的连带收益）
- skip welcome 直达 launcher，不再被 xiaozhi_xxx 热点抢占

### 6. 稳定性铁律（写入长期经验库）
1. **Wi-Fi 驱动 stop/start 切换的通知链中，禁止同步执行依赖驱动已就绪的操作**，必须延迟异步执行。
2. 日后更新 `esp-wifi-connect` 组件（idf.py add-dependency / 组件管理器），**必须复查 band_mode 调用时序**——托管组件的 patch 会被更新覆盖。
3. 排查重启类问题优先抓日志解码 backtrace，不要盲猜；本项目日志控制台已在 USB 口（pyserial 115200 直读 `/dev/cu.usbmodem1301`）。
